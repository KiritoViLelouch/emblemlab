# Version-aware data contract
Every catalog entity has stable prefixed ID, game, patch, set, mode, source, imported_at and verification_status, zh_CN/en_US names, optional icon and aliases. Pydantic rejects extra fields and all cross-game/version payloads and references. IDs are stable within this synthetic example set; real adapters need source-specific stable ID mappings.
Game: global ID TFT/JCC and display name. GameVersion: game/patch/set/mode with ruleset links. Ruleset: version provenance, duplicates, unused emblem permission, per-holder duplicate limit. Champion: cost, native trait IDs, item slots, availability, optional unlock condition. Trait: ordered nonlinear thresholds and unique-eligible counting. ChampionTrait: same-version relation represented by Champion.traits, future relational link supported. Emblem: target trait, banned holder IDs, native ownership permission. EmblemEquipRule: legality fields in Emblem + Ruleset. TraitThreshold: ordered count and cumulative utility. TraitCountingRule: unique eligible only; unsupported mechanics rejected. ReforgeRule: version-aware support flag, verified targets/pools/probabilities absent. DataSource: source identifier, attribution, permission/license status. StatisticsObservation: reserved entity kind, requires observed sample/time/source; not inferred from a guide. CommunityGuideRecommendation: separate reserved kind, recommendation provenance without fabricated samples. CrossGameEntityMapping: reserved explicit mapping kind, never implicit shared entity reference; it must carry two fully qualified game/version references and verification before future use.
Storage: Game table, VersionedRecord composite primary key (game_id,ruleset_id,kind,entity_id), required provenance columns and JSON payload. EntityLink references both endpoints using the same game/ruleset key. Cross-game mappings must use explicit payloads rather than these same-game links. Reserved kinds have no import endpoints until typed validation is implemented.
Champion/trait/emblem schemas are in app/schemas/domain.py. Catalog ruleset validation ensures referential integrity, strictly ascending thresholds, nondecreasing utility and isolated game/version metadata. Sources are synthetic; imported_at denotes fixture creation, not current patch verification.

## Phase 2 community records
`community_imports(id, metadata_json)` stores source title/URL, attribution, declared license, filename, file/catalog SHA-256, game_id/ruleset_id, patch/set/mode, sheet, imported_at, unverified community kind and row_count. `community_rows(id, import_id FK, row_number, revision, raw JSON, current JSON, history JSON)` inherits immutable batch provenance. Current values include emblem_id, holder label/ID pairs, composition aliases, issues and review status. Correction history preserves before/after snapshots, reviewer, rationale, timestamp and revision. These tables have no link to StatisticsObservation or solver inputs. See COMMUNITY_IMPORT.md for the complete contract.

## Phase 3 statistical observations
`statistics_observations` stores immutable provider IDs, exact game/ruleset/patch/set/mode columns, observed/synthetic discriminator, canonical context key, normalized input JSON, catalog/payload SHA-256, source authorization snapshot and UTC imported_at. Observed rows require a fully verified catalog; synthetic fixtures only accept explicitly synthetic rows. Provider-neutral Pydantic schemas validate cohort/time/unit/placement scale, contextual entity references, counts, rate/mean consistency, and optional reported confidence. Derived metrics/confidence/quality are computed at read time without overwriting source values. The operator-controlled source registry records permission evidence and exact permitted scopes/uses; it has no public registration API. See STATISTICS_INGESTION.md for every field and assumption.
